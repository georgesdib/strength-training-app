# WEB UI

A local browser interface over the same Python core. It is an additional surface, not a
replacement for the CLI.

**UI and functionality hardening:** request-body limits, inline-handler safety, deterministic
dates, safe error responses, data-integrity checks, browser coverage and frontend modularisation
were implemented and closed in [`UI-IMPROVEMENT-PLAN.md`](archive/UI-IMPROVEMENT-PLAN.md) on 2026-10-27.

**UI redesign:** the six-area navigation, actionable Today and integrated Progress work
(P0–P3), including the read-only data contracts and pattern-group effective control, is
implemented; the final audit closed 2026-11-06. See
[`UI-DESIGN-IMPLEMENTATION-PLAN.md`](archive/UI-DESIGN-IMPLEMENTATION-PLAN.md).

## Run

```bash
./run-web.sh                       # launcher: finds the venv, opens the browser
./run-web.sh --no-open --port 8001
./run-web.sh --db other.db

strength-coach web                 # http://127.0.0.1:8000
strength-coach web --open
strength-coach web --port 8001
```

`run-web.sh` moves `--db` before the subcommand (it is a global option in the CLI) and passes
`--host` through. It is convenience only: it ends in the same `strength-coach web`.

**Home network only, no authentication.** The default bind is `0.0.0.0`; use it only behind a
trusted home router and never forward the port. The accepted temporary risk is `LIM-57`;
authentication/per-user/TLS are planned in `ROADMAP.md` §4.19.

### Autostart (systemd)

The repository ships `deploy/strength-coach-web.service` and `tools/start_web.sh`. Install as
root after stopping any ad-hoc server on port 8000:

```bash
sudo install -m 0644 deploy/strength-coach-web.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now strength-coach-web.service
sudo systemctl status strength-coach-web.service
```

The unit runs as `dsh`, binds `0.0.0.0:8000`, restarts on failure and reads the same
`data/coach.db`. Check logs with `sudo journalctl -u strength-coach-web.service -n 50`.

## Pages

The page uses a **collapsible left menu**: the ☰ button opens it, and ×, the backdrop or Escape closes it. Navigation groups existing destinations into **Today**, **Training**, **Progress**, **Health & Longevity**, **Programme Intelligence**, and **Administration**; selecting a view opens its area and collapses the others. The selected area is announced through `aria-current`. Groups organize existing workflows rather than duplicate their forms.

- **Today** — an active-workout-aware Start/Continue action, readiness and block context, review/form-follow-up shortcuts, recent sessions, periodic review prompts, and a compact descriptive progress snapshot. The longer form follow-up is collapsed; detailed analytics are in Progress, Performance, Outcomes, and Review. The review list is fed by `config/reviews.v1.yaml`; acknowledging one writes an append-only human record and changes no threshold or flag.
- **Progress** — an integrated 4/8/12-week workspace combining the retained main-lift change table and sRPE coverage with selectable e1RM trajectories (raw daily best, trailing 3-observation median, best/latest context), selected-exercise working load/reps (basis/unit separated), weekly working sets by movement pattern and selected exercise, a hard/effective pattern-group control, weekly working sets/RIR/tonnage/residuals, exercise training dates, an observed-day calendar, and recorded training days by rolling 7-day period. A configured weekly target appears only as a reference, not a saved schedule. The existing cross-lift ratio keeps its fixed 56-day lookback. An on-demand selected-lift panel reuses read-only lagged hard-set/session-load associations; an execution panel compares original plan set totals with logged set rows for one completed app-tracked workout. Logged rows may include different roles, are matched by the frozen plan item index where available, and do not measure adherence. A separate **Prescription adherence over time** panel sums each metric's own numerator and denominator across completed app-tracked workouts: original and final set completion, repetition/load/RIR target attainment, weekly or monthly periods, exercise comparison and per-workout drill-down into History. Periods and exercises below the documented small-sample guard remain in the tables but are omitted from the trend charts. These are descriptive, not causal or prescriptive. Missing observations stay missing; charts do not interpolate. Imported sessions without frozen app-workout plans are unavailable for plan comparison. Exercise Explorer analytics cover the complete selected date range, while exact completed-session records load in duplicate-safe 50-session pages with no 50-session history cap; “All history” clears both date bounds. Pattern-group effective sets use the existing direct 1.0 plus configured indirect 0.25 credit, and match the profile's accounting setting unless the Progress control overrides it for the report. Bodyweight history uses observed readiness dates only and is shown in Longevity; missing dates are never filled. Strength, Performance and Outcomes details remain linked for further drill-down.
- **Outcomes** — read-only 4/8/12-week strength review, attendance, volume and **Prospective check**; no prescription effect.
- **Performance** — raw e1RM session bests, rolling median, series breaks, separate degraded observations, descriptive dose and explicitly configured relative-strength ratios with source-aware add/edit/delete/reset management; filters apply server-side. A read-only **[Monitoring analysis](MONITORING-ANALYSIS.md)** section runs on demand and reports dose, lagged associations, coverage and calibration transparency. Optional per-rep velocity analysis is also here. A read-only **VBT target performance** panel reports frozen-target residual cohorts, weekly residuals, band and actual/prescribed RIR evidence, within-set rep velocity drift and per-set drill-down. Cohorts stay split by exercise, scope/family, rep count and target RIR band; no cross-exercise score, prediction interval, load recommendation or autoregulation is produced. Shared SVG chart helpers support date-scaled lines, grouped bars, references/bands, exact tooltips, and keyboard/touch series toggles without adding a chart dependency. Charts show labelled axes and legends; clicking or keyboard-activating a chart opens a larger dialog with the same axes and legend. No load targets, diagnosis, decay or calibration change; VBT target bands are descriptive comparisons, and equipment changes cannot be detected because equipment is not stored.
- **Longevity** — consolidated cardio, measurement, readiness and symptom context with recorded-count and data-gap summaries. Cardio charts only ISO weeks containing logged sessions; WHO reference lines are context, and partial windows/missing logs remain visible. Measurements plot exact observed values as method-separated points without interpolation, same-day averaging, or cross-method lines; **Load older measurements** pages through exact append-only records. An observed **Bodyweight history** table uses the readiness series, including manual-over-import precedence, and never fills missing dates. Latest measurement summaries use available history, while readiness aggregates use the selected window. No clinical status judgment or prescription effect.
- **Import** — upload the training and readiness CSVs; parsed in memory, hashed and stored in
  SQLite, never written to the repository. New cumulative exports are overlap-matched against
  stored rows, so old history is not duplicated. An **After the import** panel states the
  procedure: check the report; importing alone does not require a review or a calibration.
- **Review** — read-only historical session sheet: the stored engine scores only. The rubric is
  retired (`DEC-EVAL-09`): there is no marks column, no mark form, no calibration button and no
  report. Sessions completed after the retirement show no items.
- **Workflow** — guided readiness → preview → start → active workout → post-workout comparison; owns the daily readiness form, the computed global/category score and the **Override the score** panel beside it. The panel names the date it writes (the readiness date above it), offers global or per-pattern scopes, and states that a category override wins over global and that both expire with the date. The prescription preview is also here.
- **Readiness** — baseline and policy settings; the daily log and score overrides live in Workflow;
  per-athlete baseline settings and the shadow baseline report are available; quick presets show
  their sleep/energy/soreness/stress values and an **Edit preset YAML** action edits
  `config/readiness-presets.v1.yaml` with validation before saving; the **Volume valve** sets the
  poor-readiness accessory set reduction; the volume ledger and MRV cap are on Prescribe. A
  current workout is refused until readiness is ready.
- **Prescribe** — analysis for continuity, volume, regime, fatigue, selection and validation; the prescription form lives in Workflow; the preview builds the deterministic prescription with date + session type (`auto` rolling, squat, hinge, bench+squat, bench+hinge), an optional one-session **Technique throttle** (`MOD-TECH-001`: 90% load cap and RIR floor 3 on the session's essential items, or on one named movement pattern; it never reads a form rating and stores no state), warnings and notes; every item cites
  rule ids and shows the e1RM source-set count where one exists. The page labels e1RM as an estimate, readiness as a bounded heuristic, MEV/MAV/MRV
  as configurable landmarks, the spinal cap as ordinal, and deload/minimum-session evidence
  limits. A `recent stress` column, a `readiness` column, the **strength fatigue diagnostic**
  panel (predictive form rejected; per-lift + overall state is descriptive context with 95% intervals,
  R²/status; no load effect), the **weekly volume** panel (hard sets by pattern against MEV/MAV/MRV landmarks; the MRV cap trims accessory sets; a separate heavy-spinal-set count at RIR ≤ 1 is context only; week/date controls), the **continuity calibration** panel (per-band returns/fixed/applied and the
  `allow_relax_fixed` setting, with an as-of date), the **strength fatigue diagnostic** date control and the **retrospective validation** maximum-dates control (integer 1–100, default 12, server-validated; invalid values are rejected rather than clamped), and the **exercise selection** panel (preview rankings with A/B/C
  comparison classes and a display-only own-history e1RM ratio; optional LLM chooser). Under
  the rankings it shows the **fatigue-informed suggestion** (Part C): at most one accessory
  variant, only when the exposure signal is high and the candidate is rated strictly lower on
  an in-scope demand dimension, covers the current lift's primary muscles and compares A/B;
  it is suggest-only and abstains with a reason otherwise (`DEC-SELECT-12`). The session is chosen by the rolling emphasis rule;
  **Minimum session** is an explicit volume-only fallback (30/45/60 minutes); it never changes load/RIR, preserves main lifts by default, and has a separate deeper tier for main-lift floors. **Apply selection** reruns the per-slot ranking: A candidates replace the slot exercises
automatically, **Confirm near-comparable** is required for B, and C is never applied (it is
hidden unless **show different lifts** is ticked). Each applied substitution cites
`MOD-SELECT-001` and the load is re-solved from the selected lift's own history; the session
type does not change, and nothing is persisted until Start workout. The latest preview is also
cached in this browser for seven days so a reload or navigation away can restore it. The restore
notice shows the cached date/session beside the current form values; **Start cached plan**
requires an explicit confirmation, and corrupt or future timestamps are rejected. A cached plan
whose date/session no longer matches the form is discarded, and changing the form selection
invalidates the cache immediately. The Workflow
build itself runs as a polled background job and shows elapsed seconds, so a long resolver build
cannot end in a browser load failure. The cache is
not a server-side prescription and is cleared when the workout starts. **Use LLM** appears only when Apply is ticked. Without the toggle the
  prescription is unchanged. The **Retrospective validation** panel runs the walk-forward check. A scheduled deload is shown as a suggestion with an **Apply deload** button; it is not applied until confirmed. Reactive deloads are automatic. Applied deloads cite `MOD-DELOAD-001`. Main lifts show their warm-up ramp; the strength-test cadence is shown in the notes. The volume ledger now applies `MOD-VOL-002` (one accessory set after three weeks below MEV). When a trustworthy calibration exists, each prescription item has an expandable **VBT** target showing the median velocity, robust calibration band, rep count, RIR band, lift/family scope, sample size, method version and calibration id. A missing target is stated with its reason; no target is invented and no legacy target is reconstructed.
- **Outcomes → Form trend** — current vs previous equal window, latest rating, change and
  session counts; descriptive only.
- **History** — paginated list of training days, each expandable into its session fragments, with date filters, fragment detail and append-only correction. Attendance and day totals count each local date once; fragments keep their own ids, sets and edits. Edits rebuild totals/critique and mark the fragment re-review; date/type are fixed. For completed app-tracked workouts, **Session details** includes a read-only **Prescription adherence** section: original and final modified prescriptions side by side, prescribed/performed/filled/missing/extra working sets, set completion with its numerator and denominator, rep/load/RIR target attainment, expandable per-exercise and per-set target-versus-actual detail, prescription changes, unmatched work and data-quality limitations. Set completion is labelled separately from target attainment, and unavailable comparisons are stated explicitly. Imported or voided sessions show an explicit unavailable reason. The section is derived from the completed clean_set leaf rows, so an audited correction is reflected; it never writes or changes a prescription. The same detail includes an expandable **VBT target comparison** per exercise: historical target and band, actual mean velocity, signed/relative delta, within/outside-band status, comparability and exclusion reasons, actual/prescribed RIR, and per-set source (final/original plan, stored/override velocity). With-in-set velocity loss remains separate. The edit sheet carries optional per-lift **Form** 1–5 ratings and an
  optional note; saving appends a correction so imported and live sessions can be rated or
  overridden. A blank rating means **leave the existing rating and note unchanged**; the sheet
does not remove ratings. Review shows the current rating beside up to five prior ratings for
the same lift.
- **Workflow → Workout** — start from the preview with a score-ready assessment or an explicit unknown/partial acknowledgement (device fields optional), log sets manually, remove a set, end with measured/manual duration and sRPE or mark sRPE not recorded, or abandon. A prescription snapshot is frozen at start. During the workout the plan is editable: adjust planned sets, swap/add/remove exercises; swap opens one searchable exercise dialog, each add/swap is an append-only event and the original prescription stays frozen. On completion the workout materialises, the end screen shows actual vs modified plan, actual vs original prescription, a per-exercise VBT target-versus-actual comparison, the deterministic rubric, and a descriptive Phase 2 summary. **Review workout** opens the rubric sheet; saving marks runs calibration and closes the workout. In-workout CSV import is available by paste or file with columns `Exercise,Set,RPE,Value,Weight,Reps`; preview first, then apply. A recognised exercise absent from the prescription is added to the workout plan; an unrecognised exercise is shown as unknown and blocks apply. The file has no date, so backfill is not supported. Plan cards show expandable VBT target provenance. The logger's planned-target area checks the selected exercise, set group, rep count and actual RIR: a target is never shown as applicable when the performed reps differ from its calibration rep count, and an effort outside the target band is labelled not comparable. After a velocity-bearing set is logged, a compact inline feedback line shows target, actual, signed/relative difference, calibration-band status and whether the comparison is valid; it is descriptive, not a coaching judgment or a termination rule. Each planned lift has an optional **Form** 1–5 rating, editable later in History. An optional second per-rep CSV (`Exercise Name,Set Number,Metric Name,Rep Number,Velocity`) can be added in the same panel; it joins by exercise + set, never creates a set, and is shown descriptively after the workout. The ended screen also offers an optional **e1RM**
  record: a measured test from a set (kg x reps, which registers a high-intensity exposure and
  rejects a 1RM until the interval allows it) or a direct override. Both append; nothing is edited.
  **Start another session today** creates a second fragment on the same date, linked to the same
  day plan and the first fragment's readiness snapshot; it does not create a second plan.
- **Workout → per-exercise history** — every planned lift has a **History** toggle. It lazily shows
  the last five completed sessions (newest first) with set number, load × reps and RIR, and a
  **Show more** control for the next five. It includes declared history equivalents (currently
  back extension/hyperextension), excludes warm-ups, voided sessions and superseded sets, respects
  the workout date, and is read-only; current workout sets are not part of it and corrections stay
  in History. The *Plan and plan edits* section is open by default so the toggle is visible.
- **Programme** — rolling session-type forecast; choose weeks, sessions/week, optional start
  date and first session type (`auto` or a specific type).
  Every session is a projection rebuilt on the day; no future plan is persisted or promised.
- **Cardio** — log a session (modality, minutes, HR, distance, sRPE) choose the window (4/12/26/52 weeks) and an optional as-of date:
  sessions, total/average minutes, weekly breakdown and a chart of weeks with logged minutes. Weeks with no entries are omitted rather than represented as zero or proof of inactivity; boundary weeks may be partial. WHO reference lines are context only. Capture only; no load changes.
- **Measures** — periodic outcomes (VO2max, grip, body fat, 5x sit-to-stand, steps, sitting),
  with latest value, change and entries, filtered by metric. Every metric with recorded values gets its own chart; a **Chart window** control selects the last 3, 6 or 12 months or all history, and each chart pages through that metric's entries (200 per request) so the window is complete. Metrics without data show no chart. Charts plot independent events, separate methods (including “method not recorded”), and do not average same-day observations or connect/infer values. Metrics and directions are config; nothing changes a load.
### Progress snapshot ratio (Today)

The Today **Progress snapshot** (and `GET /api/progress`) reports a descriptive session
performance ratio:

- for each eligible lift in a session: the session's best e1RM ÷ that lift's best e1RM in the
  preceding 84 days (strictly before the session);
- the session value is the median of those lift ratios (a session with one eligible lift uses
  that lift);
- the snapshot uses sessions in the last 56 days. **Latest ratio** is the newest session,
  **recent ratio median** is the median over all of those sessions, and `n` is their count.
  The chart plots at most the last 12 points.

`1.000` means the session matched the prior best; values above or below are relative to that
history, not a verdict. Only loaded working sets with a usable e1RM (reps 1–20, not voided or
superseded) enter; a lift with no prior e1RM in the 84-day window contributes no ratio, and a
session with no eligible lift produces no point. It is descriptive: not a measured test, not a
target, not an injury signal, and it never changes a prescription. e1RM is an estimate, so the
ratio inherits its precision limits.

### Exercise Explorer history

- **Exercises** — full canonical catalogue with search/filter and one **Open** action per row for
  add/view/edit in the same dialog. Pattern, VBT family and primary muscles are constrained
  controls (VBT offers existing families plus an explicit new-family path); additional-properties
  JSON is under an advanced disclosure. Edits are written to `config/exercises/overrides.v1.yaml`;
  existing ids are immutable. The dialog includes descriptive per-lift e1RM (raw estimates plus
  rolling median), working-set-count-by-training-day, load-by-basis and repetitions-by-recorded-unit
  charts. Choose an inclusive date range or **All history**; summary charts and coverage use the
  complete selected range, while exact records are loaded in pages of 50 sessions until exhausted.
  Same-day fragments are combined for descriptive daily analytics; load bases and repetition units
  are kept in separate charts, exact medians are shown in point tooltips, and no dates are imputed.
  None changes prescription behavior.
  e1RM-ineligible lifts and missing histories have explicit empty states.
  Each row carries a **Demands** count (`rated/4` in-scope dimensions) and the details dialog
  shows the demand profile with level, confidence, reason and cited evidence ids, plus the
  catalogue digest and whether the git-ignored local overlay is active
  (`docs/EXERCISE-DEMANDS.md`). The profile is editable there: **Rate this dimension** writes
  `config/exercises/demands.local.yaml` through `POST /api/exercises/demands` (same
  `set_claim` the CLI uses), **Clear local rating** removes the override, and a rejected write
  leaves the overlay untouched. The **Evidence** list offers only ids the reviewed file
  defines (with citation tooltips) and is required for `supported`, so the browser cannot
  invent a source; the reviewed file is never edited from the browser. It is a checkbox list,
  not a `<select multiple>`, because iOS Safari renders a multiple select as "0 items" no
  matter what is ticked. The form opens on the selected dimension's saved claim — level,
  confidence, reason and cited ids are preselected and a live `N selected` count follows the
  choice — so saving cannot silently look empty or drop an existing citation.
  A row's **e1RM** button opens an override panel for that lift: it shows the override currently
  in force and appends a new one (kg, effective-from, reason) through the same endpoint the
  Athlete page and `e1rm set` use, so the next prescription cites it.
- **Athlete** — append-only editing of profile (including the **Exposure trim** switch, off by
  default; `DEC-EXPOSURE-02`; a profile edit that does not mention it preserves its value),
  constraints, suitability, e1RM overrides,
  strength tests, block start and symptoms; the symptom form supports an optional
  athlete-attributed session, performed lift, onset and confidence, with a session picker
  limited by the configured lookback. It shows the current tables, injury signal, a separate
  athlete-attributed symptoms block and the **e1RM calibration** report (current formula e1RM and last set for every lift, plus
  measured tests vs formula; a bounded correction is applied only when the confidence interval
  excludes 1.0). Read-only preview controls change the calibration/coverage window without
  changing active calibration, the raw symptom history shows the latest 10 with Show all, and
  the strength-test cadence block reports last/next/due state. Cadence and measured-test
  coverage are shown separately; coverage reuses the e1RM coverage gate (current, insufficient
  or unavailable) with an explanatory reason. **Record a strength test** scrolls to and focuses
  the existing dynamically rendered `#test-form`; it does not create a second form or submission
  path.
- **Prescribe → Regime change** — read-only 8-week check for a main lift disappearing while a
  same-category substitute rises; a review question, never an action.
- **Settings** — appearance (System / Light / Dark), optional LLM configuration (enable/disable, model, endpoint, write-only key,
  temperature/tokens/timeout), an **iOS settings** panel for `config/ios.v1.yaml` (`mutations_enabled`, issued-plan TTL, plan-request TTL and receipt retention; integer/boolean controls with server ranges, effective values, source and per-request reload, so no restart is needed), browser-only Prescribe defaults, a collapsed read-only **Monitoring & reports** inventory with search/group filters, a dedicated **Resolver** panel (append-only scalar settings with explicit enable confirmation, validated structural YAML with backups/digest, read-only preview with alternatives/suggestions, unrated suggestions shown provisionally with inline suitability rating and a Start handoff blocked until they are rated; the preview runs as a polled background job so a long resolver build cannot end in a browser load failure), and read-only app/database paths.
  The key is masked and lives in git-ignored `config/llm.local.toml`.
- **Logs** — manually refreshed recent tail, capped at 500 records in process memory and cleared
  when the server restarts; this is not a durable audit history or system-health monitor.
- **Docs** — local Markdown rendered without external assets.

## Design

The web layer is serialisation and routing only. It calls the same functions as the CLI:
`build_prescription`, `workout.summary`, `adherence.analyse`, `observations.analyse`,
`record_manual` and the reporting services. A missing value is still `unknown`; the UI does not
fill it in.

## Manual browser smoke checklist

No browser automation is installed. Run this pass manually after any UI change; record the
result in the change note. It is not a substitute for the HTTP and static tests, and a skipped
browser check is not a passed browser check.

1. Load `/`, open every primary nav view, and confirm the console has no errors and no static
   request 404s.
2. Open a docs deep link from a panel and from the Docs view; use the browser Back button.
3. Save readiness for today, reload, and confirm the values and date survive. Apply a quick
   preset and confirm it writes ordinary fields.
4. Generate a prescription, inspect warnings and the volume panel, then start a workout.
5. Add one set, then double-click the Add set button; confirm only one set appears. Edit a set,
   remove one, and end the workout.
6. Open History and Review; confirm the persisted session, sets, duration and any form rating.
7. In History, open Session details for a completed app-tracked workout. Confirm the
   Prescription adherence section shows original and final prescriptions separately, set
   completion beside target attainment, expandable exercise/per-set detail, prescription
   changes, unmatched work and data-quality notes. An imported or voided session must show the
   explicit unavailable reason, not zeros.
8. Import a small training/readiness pair; check the preview, apply it, then re-import to confirm
   the idempotency message rather than duplicate rows.
9. Stop the server or block one request and confirm the UI shows an error instead of silently
   succeeding.

### Mobile pass (iPhone-class viewport)

Run at 440 x 956 and 956 x 440 CSS pixels, in both orientations:

1. Confirm the document does not scroll horizontally. The active workout plan and set list
   must be cards; the plan and import sections must be collapsed by default.
2. Confirm the set logger is the first actionable section after the workout header. Add two
   sets of the same lift and check that the exercise and values persist, with the planned
   target and next set number visible.
3. Check that readiness endpoint labels and the Workflow presets are visible, including their
   sleep/energy/soreness/stress values; stress and soreness must read 5 = none. Open the preset
   YAML editor, save a valid edit, and confirm the buttons reload with the new values.
4. Open the menu and a details dialog; confirm focus moves in, Tab stays inside the menu,
   Escape/close restores focus, and dialog text is readable in light and dark themes.
5. Rotate during a partial readiness form and a partial set entry; values must survive.
6. Confirm the Today "Start today's session" action opens the current Workflow stage.
7. Check that removing a set or planned exercise asks first, and that the error message is
   announced and the offending field is marked invalid.
8. Open Review on the phone and confirm each rubric item is one card with a single score input,
   with anchors and the long explanation behind disclosures. Use the workout Swap action and
   confirm one searchable dialog opens rather than a long select per card.
9. Open History → Session details. The original/final adherence cards must stack, the per-set
   tables must scroll inside their frame without scrolling the page body, and status badges must
   remain readable in light and dark themes.

A skipped browser check is not a passed browser check. Native Safari keyboard and picker
behaviour still require a physical-device pass.

## Limitations

- UI prescription previews are read-only. Starting a workout commits the plan as a stored
  prescription, its items and modifier provenance in one transaction. See `docs/UI-CLI-PARITY.md`.
- No LLM proposal/chat UI today; proposals remain CLI-only (`run --propose`). A future phased plan for analyst, explainer and constrained-proposer surfaces is in [`docs/LLM-INTEGRATION-PLAN.md`](LLM-INTEGRATION-PLAN.md); it is not implemented and does not change the current limitation.
- Remaining first-class parity gaps (bulk review, state YAML import, report window controls)
  are listed in `docs/UI-CLI-PARITY.md`.
- Workout mode is UI-first for start; CLI covers status/add/update/remove/end/import. Completed workouts materialise into `session`/`clean_set`; review/rubric is built.
- State editing is available; the taxonomy itself and programme rules remain config/CLI.
- The **Logs** page shows the in-memory application/HTTP tail (`/api/logs`); it is a local
  diagnostic surface and resets when the web process restarts.
- When **Use LLM** is requested without a configured model, the prescription carries a warning
  and `selection.llm_unavailable = true`; the UI says that NullLLM fallback was used.
- The Programme page uses the **job + sessionStorage cache** path. The cache key includes the
  app version, request, resolved profile, database revision and relevant config hashes, so a
  profile/config change or a database write cannot reuse an old forecast. Settings has a
  **Clear cached forecasts** button; entries otherwise live for the browser tab and have no
  TTL. The cache is transport-only: the CLI rebuilds the same deterministic forecast directly
  and has no cached-forecast command (`LIM-27`).
- No authentication; home-network HTTP only, never public. The separately authenticated
  `/api/ios/v1/` facade is for the native iPhone client, not this UI.
- iPhone pairing and device revocation are CLI-only (`strength-coach ios ...`); managing phone
  credentials is a host-level security action, so the web UI does not expose it.
- No delete/void action for a completed workout; only active-workout abandon and set removal/edit. See DATA-MODEL §17 for the recommended void design.
- Execution telemetry (set/rest/exercise timing) is captured by the native iPhone client.
  Completed-workout **Details** in this web UI also shows a read-only graphical timeline, set
  timing and prescribed-versus-actual rest via `/api/history/<id>/execution`. It is descriptive,
  never a fatigue or compliance score.
