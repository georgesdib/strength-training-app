# How Workout Generation Works

This document explains how Evidence-Based Strength Coach turns stored training data and today's inputs into a prescription. It describes the intended and implemented decision flow in plain English; detailed thresholds, configuration and evidence remain in the linked technical documents.

## 1. The core principle

**Python calculates; the optional language model explains or makes bounded choices.**

The prescription is not generated by asking a chatbot to invent a workout. The engine follows configured templates, data-selection rules and a citable set of programme rules. It calculates loads, rep/RIR targets and other numeric outputs deterministically, validates the result, and records the provenance. An LLM may provide narrative or choose among precomputed, validated alternatives. It cannot calculate or write a load, RIR or velocity number, and it cannot veto a rule.

The system is designed to work without an LLM. With the model disabled or unavailable, the deterministic prescription still runs; the optional explanation or selection capability may be absent.

## 2. Inputs that can affect a prescription

| Input | What it contributes | Important limitation |
|---|---|---|
| Athlete state and goals | Programme context, current block, constraints and preferences | Must be kept current by the athlete |
| Exercise suitability and hard constraints | Removes or restricts exercises the athlete has ruled out | A high readiness score cannot override a hard constraint |
| Training history | Recent sets, reps, loads, session sequence and exercise exposure | Imports may contain backfilled data and may lack reliable timestamps |
| e1RM data and overrides | Load estimates for the relevant lift or permitted variant | An e1RM is an estimate; variants may not be directly comparable |
| Readiness | Day-specific downward adjustments to load/effort and, under configured rules, accessory volume | Weights and cut-points are not validated individual thresholds |
| Symptom/injury context | Conservative ceilings or warnings for exercises linked to a symptomatic region | This is not diagnosis, medical clearance or an injury predictor |
| Programme templates | The session's slots, exercises, sets, rep ranges, RIR, rest and load source | Template edits require validation and may change prescriptions |
| Configuration and rule set | Increments, rounding, volume landmarks, spinal-cost limits and other policies | These are explicit design choices, not all empirically validated |
| Optional user choices | Session type, minimum-session mode and other supported controls | User convenience cannot override hard rules |
| Optional LLM | Narrative and selection among allowed options | Cannot calculate numeric prescriptions or veto policy |

Cardio and body measurements can be recorded as context, but the app does not prescribe cardio and does not automatically make those records training targets.

## 3. The decision pipeline

The canonical flow is documented in [`METHODOLOGY.md`](METHODOLOGY.md). In broad terms:

1. **Resolve athlete state and constraints.** The engine loads current goals, suitability ratings, explicit exclusions, block information and other state. Hard constraints are policy boundaries, not suggestions.
2. **Resolve readiness for the requested date.** The readiness record is date-scoped. If a score is unavailable, the UI requires the supported acknowledgement rather than silently treating missing data as normal. Readiness may only move the prescription in a more conservative direction.
3. **Choose the session type.** The rolling sequence uses four canonical types: `squat`, `hinge`, `bench_squat`, and `bench_hinge`. A user may select a supported type. The Programme view is a projection; the actual day's prescription is built when requested.
4. **Select exercises within the template.** Each session type has ordered slots. Some slots allow variants. The selector may choose only configured alternatives that satisfy the app's comparability and suitability rules; it does not freely invent exercises.
5. **Resolve the load source.** A slot may use an e1RM-based load, double progression, or bodyweight according to its configuration. The engine uses the relevant stored estimate, permitted override, or recent performance data. It applies the configured formula and rounds down to valid loading increments.
6. **Set reps and effort targets.** Rep ranges and RIR windows come from the selected template and programme rules. RIR means estimated repetitions in reserve; it is not a directly measured value.
7. **Apply modifiers in a defined order.** Readiness, continuity-related logic where applicable, deload policy, volume management, spinal-load constraints and a supported minimum-session option are applied according to the methodology. A later convenience must not undo an earlier safety rule.
8. **Build warm-up guidance.** The system may include a standardised warm-up ramp derived from the working prescription.
9. **Validate the candidate.** The prescription is checked against hard constraints, effort windows, spinal-cost limits, template requirements and whether the resulting session is executable.
10. **Attach advisories and provenance.** The output can include e1RM plausibility, injury-signal and recent-stress advisories. The prescription records the rules or stored sets supporting its values.
11. **Return the prescription and optional explanation.** Numeric values come from Python. Any LLM narrative is supplementary and does not replace the structured output.

The most restrictive applicable rule wins. Missing information should remain `unknown`; it must not be silently converted to zero or a normal result.

## 4. Session types and templates

The shipped programme has four canonical session types:

- `squat`
- `hinge`
- `bench_squat`
- `bench_hinge`

The templates define the ordered slots and their exercise or permitted variants, working sets, rep range, RIR window, rest, essential status, load source and any power-specific fields. They also define a time budget used for estimation. The template is not the same thing as the full prescription: the engine may select a permitted variant, solve a load, and apply modifiers before validating the final session.

A power slot uses a quality stop rather than a conventional RIR target. Its purpose is high-quality, high-intent work, not fatigue accumulation. Stop according to the prescribed quality rule; do not continue just to complete a number of poor repetitions.

Template edits are validated as a whole. Unknown exercise IDs, malformed slots and invalid power/RIR combinations should be rejected. A successful template edit affects future prescriptions, not historical prescriptions already stored. See [`SESSION-TEMPLATES.md`](SESSION-TEMPLATES.md).

## 5. How loads are calculated

For an e1RM-based slot, the engine chooses a relevant estimate or permitted manual override and uses the configured load-solving method, including the prescribed repetitions and effort target. It then rounds down to valid equipment increments and validates the result.

Other slots may use double progression: the athlete accumulates reps within the prescribed range at the required effort; when all sets meet the configured progression condition, the load can increase by one increment. Bodyweight slots use their configured bodyweight load source.

The app deliberately does not treat every exercise variant as interchangeable. A variant must satisfy the selection and comparability rules before its history can support the load. A recent result on one exercise should not automatically be interpreted as an equivalent result on a mechanically different one.

The exact formulas, selection windows, thresholds and rounding rules are implementation/configuration details. Consult the current code, rules and [`METHODOLOGY.md`](METHODOLOGY.md) for those details rather than relying on a general explanation as a formula specification.

## 6. Readiness: a modifier, not the programme

Readiness combines available subjective inputs and optional device context according to a fixed configured policy. The core subjective fields include sleep, energy, mood, soreness and stress. HRV and resting heart rate are interpreted relative to an athlete-specific baseline when enough data exists. An optional wearable score can be blended in, but it is not a replacement for the subjective inputs.

Readiness can lower prescribed loads and allow more repetitions in reserve. Poor readiness can remove an accessory set under the implemented rule. Main-lift set reduction is a separate opt-in setting. A readiness score is not a validated per-lift readiness measurement, and the weights/cut-points are design assumptions. Readiness does not clear injuries, make an unsuitable exercise suitable, or override a hard constraint.

For details, see [`READINESS-SCORE.md`](READINESS-SCORE.md) and [`LIFT-READINESS.md`](LIFT-READINESS.md).

## 7. Volume, spinal cost and deload policy

The programme tracks recent working sets by movement pattern against configured MEV/MAV/MRV landmarks. These are broad coaching guardrails; they are not measured individual thresholds. When the proposed session would exceed the configured MRV, the cap trims non-essential sets first. Essential work is not automatically removed simply to make the arithmetic fit; if essential work alone remains above the limit, the system warns.

The app also applies configured spinal-cost rules. Spinal cost is an ordinal, load-blind measure: it is a way to constrain the mix of exercises, not a measurement of spinal force or tissue stress. The user should inspect the planned work and its warnings, especially when symptoms or back history are relevant.

Deload policy is separate from the volume ledger. A scheduled deload can be configured, and reactive triggers may suggest one under the implemented policy. The evidence does not establish a universally optimal deload schedule. See [`VOLUME-MANAGEMENT.md`](VOLUME-MANAGEMENT.md), [`LONGEVITY-REVIEW.md`](LONGEVITY-REVIEW.md), and the decision records for the current policy.

## 8. Injury and symptom context

The injury signal uses recorded symptoms and exposure to exercises that load the relevant region. It can show statuses such as unknown, insufficient, active, monitoring or review, and may add a warning or ceiling according to the configured policy.

This signal is intentionally conservative but limited:

- it does not diagnose the cause of symptoms;
- it does not prove that a tissue has healed or that an exercise is safe;
- absence of a symptom entry is not evidence of no symptoms;
- a `review` status does not automatically change suitability ratings or remove constraints;
- the exercise-to-region map represents exposure, not proof that a lift caused a problem.

For current rules and caveats, see [`INJURY-SIGNAL.md`](INJURY-SIGNAL.md). Seek appropriate clinical advice for concerning symptoms rather than relying on the app.

## 9. Minimum-session and time constraints

Where supported, the user can choose a minimum-session option to make a workout more feasible when time is limited. This is a planning aid, not a measured guarantee of session duration. The standard tier removes non-essential accessory work first; a deeper tier may reduce main-lift sets to the configured floor. It preserves load and RIR targets and cannot override hard constraints.

The time estimate depends on template time budgets, work slots and configured assumptions. The generated prescription and active workout show it at the top as a planning estimate; it excludes transitions and idle time. Actual duration is only captured when recorded, such as in live workout mode. See [`MINIMUM-SESSION.md`](MINIMUM-SESSION.md).

## 10. What calibration does—and does not do

The app has distinct reports that should not be conflated:

- **Rubric calibration** compares the engine's session-critique scores with human marks.
- **Readiness calibration** compares the readiness score with historical readiness labels.
- **Baseline shadow** compares the current HRV/RHR baseline approach with an alternative trend projection.

These are diagnostic reports. They do not automatically retune the rubric, readiness weights, safety thresholds or programme policy. Importing history alone does not produce human calibration labels; review sessions first if you want rubric agreement to be measured.

The reports describe agreement with available labels. They do not establish that the rubric predicts future performance, prevents injury, or improves health outcomes.

## 11. Evidence status and limitations

The app is evidence-informed, not prospectively validated as a complete coaching system. Some components have research support at a broad level, but exact implementation details often remain design assumptions. Examples include readiness weights and cut-points, movement-pattern volume landmarks, the ordinal spinal-cost scale, some selection rules and the interaction of multiple modifiers.

Important limitations include:

- imported logs may contain backfilled entries and unreliable timestamps;
- e1RM estimates contain individual and variant error;
- missing data can limit readiness and injury interpretation;
- symptom entries are self-reported and may be absent;
- retrospective agreement with human marks is not prospective validation;
- single-athlete observational records cannot establish causation;
- the app is not a medical diagnostic, treatment, clearance or injury-prediction system;
- the app does not prescribe cardio.

The programme should therefore be treated as an inspectable decision aid. Check the output, use judgement, and report actual outcomes if you want the tool to have a meaningful history to review.

### 12.5 What the example demonstrates—and what it does not

It demonstrates that the engine:

- chooses only exercises configured for the requested session type, and selects among allowed variants using the recorded history;
- calculates main-lift loads from an RIR-adjusted e1RM and the template's rep/RIR target, then rounds down to the available increment;
- uses the configured progression source for accessories and preserves bodyweight semantics;
- applies the under-MEV accessory top-up: the four-set accessories in §12.3 are not the template's three sets, because `MOD-VOL-002` added one set to each;
- reports readiness as unknown when no dated row exists, rather than inventing a score or claiming a readiness downgrade;
- records provenance, a time estimate and the spinal-cost position for the run;
- can attach a readiness modifier and re-solve loads when the required dated input exists.

It does **not** demonstrate that the e1RM equation, readiness policy, volume landmarks, or complete programme have been prospectively validated, nor that the prescription is optimal for an individual. Those are separate empirical questions.

### 12.6 The poor-readiness comparison

The poor-readiness run in §12.4 uses the same fixture and date with one addition: `Sleep = 2` for `2024-01-08`. The engine raises the target RIR to 3, applies the 5% readiness load multiplier after re-solving, and removes one set from each non-essential slot. The `under_mev` note is false, so the under-MEV top-up does not restore the cut sets.

The named regression test `tests/test_prescribe.py::test_a_readiness_set_cut_is_not_undone_by_the_under_mev_top_up` covers the same cut-versus-top-up interaction on the `squat` session, where the accessory is below MEV; it is not the hinge run shown here. The precise load change and final prescription should always be read from that run's output, not inferred from a readiness score alone. The rule is intentionally conservative, and the threshold is not a validated individual fatigue threshold.
